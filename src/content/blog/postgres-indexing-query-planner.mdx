Adding an index to a slow relational database query is often treated as a silver bullet. Yet, junior engineers are frequently surprised when PostgreSQL completely ignores their new index and executes a full sequential scan instead.

Understanding how the cost-based optimizer evaluates query execution plans is critical to designing high-performance relational architectures.

---

### Anatomy of an Optimizer Decision

PostgreSQL calculates plan costs using configurable cost units (`seq_page_cost = 1.0`, `random_page_cost = 4.0`). If the optimizer estimates that an index lookup will touch more than roughly 10–15% of the total table rows, it deduces that random disk I/O through the B-Tree index is more expensive than reading sequential pages from disk directly:

```sql
-- Forcing index-only scans by adding covering INCLUDE columns
CREATE INDEX idx_orders_customer_covering 
ON orders (customer_id, created_at DESC) 
INCLUDE (total_amount, status);
```

---

### Eliminating Heap Lookups with Index-Only Scans

When you inspect a slow query using `EXPLAIN (ANALYZE, BUFFERS)`:

1. **Index Scan**: Traverses the B-Tree index, then fetches corresponding tuples from the table heap to retrieve missing columns.
2. **Index-Only Scan**: Retrieves all requested columns directly from the index leaf nodes, completely bypassing heap memory buffers if the visibility map confirms the page is all-visible.

By adding `INCLUDE` columns for queried projections, our telemetry analytics query execution dropped from **1,240ms** to **18.2ms**, reducing buffer hits by **98.4%**.

---

### Maintenance Rules

- Regularly monitor `pg_stat_user_indexes` to prune unused indexes that add write overhead to updates.
- Keep table statistics updated via auto-vacuuming and targeted `ANALYZE` after massive data loads.
