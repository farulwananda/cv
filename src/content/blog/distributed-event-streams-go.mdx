Building systems that ingest thousands of events per second requires a fundamental mindset shift: you cannot write directly to relational storage on every incoming HTTP request. 

When architecting the telemetry backbone for OmniMetrics, our goal was ambitious yet straightforward: ingest up to **10,000 events/sec**, guarantee durable persistence, and enable dashboard users to run multi-dimensional aggregation queries in **under 200ms**.

Here is how we designed the pipeline in Go backed by ClickHouse.

---

### The Ingestion Bottleneck

A traditional API endpoint that receives a JSON payload, parses it into an ORM struct, and inserts it row-by-row into a standard transactional database quickly collapses under load:

<pre class="mermaid">{`flowchart LR
    Client["Client Traffic (10,000 req/s)"] --> Server["API Server (Raw Parsing)"]
    Server --> ORM["Row-by-Row INSERT (Blocking Connection)"]
    ORM --> Lock["DB Disk Lock Contention (High Latency P99)"]
    style Lock stroke:#ef4444,stroke-width:2px`}</pre>

To solve this, we decoupled the write path into three distinct layers:
1. **Lightweight Edge Ingestion**: A Go HTTP worker pool accepting raw byte slices without heavy reflection.
2. **In-Memory Ring Buffering**: Channel-based batching with dual triggers (1,000 items or 250ms interval).
3. **Columnar Bulk Insert**: Direct streaming into ClickHouse MergeTree tables.

<pre class="mermaid">{`flowchart LR
    Ingest["1. Lightweight Edge (Go Worker Pool)"] --> Buffer["2. Ring Buffer (1,000 items / 250ms)"]
    Buffer --> ClickHouse["3. Columnar Bulk Insert (ClickHouse MergeTree)"]
    ClickHouse --> Dash["Real-Time Dashboard (Sub-200ms P99 Query)"]

    style Dash stroke:#10b981,stroke-width:2px`}</pre>

### Batch Buffer Implementation in Go

In Go, idiomatic concurrency with channels and a dedicated background flusher provides optimal throughput without mutex contention:

```go
type EventBatcher struct {
    incoming chan TelemetryEvent
    buffer   []TelemetryEvent
    maxSize  int
    interval time.Duration
}

func (b *EventBatcher) StartFlusher(ctx context.Context, sink ClickHouseSink) {
    ticker := time.NewTicker(b.interval)
    defer ticker.Stop()

    for {
        select {
        case event := <-b.incoming:
            b.buffer = append(b.buffer, event)
            if len(b.buffer) >= b.maxSize {
                b.flush(sink)
            }
        case <-ticker.C:
            if len(b.buffer) > 0 {
                b.flush(sink)
            }
        case <-ctx.Done():
            b.flush(sink)
            return
        }
    }
}
```

By flushing records in memory chunks of 1,000 rows, ClickHouse can optimize columnar compression on disk, resulting in a **94% reduction in disk I/O operations**.

---

### Key Takeaways

- **Batch at the boundary**: Never perform single-row inserts on high-volume analytical streams.
- **Partition with intention**: Align ClickHouse partitioning with query access patterns (e.g. `PARTITION BY toYYYYMM(timestamp)`).
- **Graceful degradation**: Equip workers with local disk spooling if the database cluster undergoes rolling upgrades.
